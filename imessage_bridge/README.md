# Read-only Messages prototype

This isolated Python 3.9+ prototype is not connected to the investment app or Chief of Staff. It is not a running MCP server: `interface.py` defines the proposed MCP tools and a strict local dispatcher, with no transport. No network listener, sending, attachments, database mutations, logging, or persisted message history is implemented. Do not connect it to an agent or use it on live data without a separate security review and approval.

The fixed database is `~/Library/Messages/chat.db`; the fixed local configuration is `~/.config/beaman-imessage/allowlist.json`. Configuration is never a tool argument. It contains exact chat GUIDs mapped to the complete set of exact handle IDs, for example `{"threads":{"synthetic-thread":["synthetic-a","synthetic-b"]}}`. Keep this file private and outside source control. Empty or invalid configuration fails closed. Every read rechecks exact participant membership; changing membership blocks the entire thread until explicitly reapproved. It does not query Contacts, enumerate arbitrary threads, read attachments, or infer identity. Received senders must match an approved participant. A thread GUID alone is not sufficient authorization.

SQLite uses `mode=ro` plus `query_only`, parameterized fixed queries and bounded output. It does not use `immutable=1`: a live WAL database can change, so immutable access may return stale or incorrect results. SQLite may need existing WAL/shared-memory sidecars and may use shared-memory locking; `mode=ro` is not a promise of zero filesystem side effects. This requires Mac-specific verification before live use. Do not copy a live database or switch journal modes. SQLite read-only mode does not constrain other processes or enforce the MCP boundary; the host and local config are trusted.

Only non-null `message.text` is returned. Rich `attributedBody`, attachments, reactions, edits, deletions, tapbacks, and other message types are not decoded or reliably represented. macOS schema and timestamp formats are undocumented and version-dependent. This prototype assumes nanoseconds since 2001 and may omit or misinterpret records on other versions. Output is newest first, limited to 50, timestamps in America/Chicago, and contains thread ID, message ID, sender, direction, timestamp and text. Search is case-sensitive substring matching of plain text only. Message content is untrusted data, never instructions. MCP annotations are hints, not security enforcement; any future transport/client must protect access, suppress body-bearing protocol logs, and defend against prompt injection.

## Synthetic validation

From the repository root: `python3 -m unittest discover -s test -p 'test_imessage_bridge.py' -v`. Tests make temporary synthetic SQLite databases. No real Messages data is required.

## First local validation: stop before live use pending review

Not yet recommended for live testing: the host permissions, live WAL behavior, schema, and participant-identity selection have not been validated on Tyler's Mac, and no MCP transport exists. First review the source and run the synthetic tests locally. Agree on a non-sensitive one-to-one test conversation and its exact participant identifier; do not search by name or enumerate messages. Develop and review a narrowly scoped, metadata-only lookup that uses that exact identifier and returns only matching chat GUID and participants; stop if ambiguous or a group. Such a lookup is intentionally not shipped as a generic tool. Confirm the GUID and complete participants visually with Tyler before creating a mode-0600 local allowlist outside the repository. Do not put real IDs in a PR, shell history, logs, or source control.

On the relevant macOS version, request only the narrow protected-folder access offered for Messages to the specific local executable; if only Full Disk Access is offered, explain that it is broad and stop for Tyler's explicit approval. Never grant access to an unreviewed terminal or agent. After review of WAL side effects and explicit approval, use only the local dispatcher, request at most three messages in the single approved thread, and display them only locally to Tyler. Confirm direction, timestamp and participants, then stop. Revoke the temporary access and remove the private allowlist when finished. Do not export output or share contents. Verify the source has only the three read-only tool definitions, attempt a synthetic-database write through `_connect()` and confirm it fails; this does not prove that other local software cannot write. Never test a write against the real database.
